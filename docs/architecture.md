# Архитектура DotaRise, этап 1

Модульный монолит: один процесс FastAPI, одна PostgreSQL, отдельный React frontend. Слои backend: API → сервисы → репозитории → SQLAlchemy. OpenDota — источник публичной статистики; Steam OpenID — только удостоверение личности. Публичный поиск не требует аккаунта. Пользователь видит источник, время получения и размер выборки.

## Поток статистики

`GET /api/players/{id}/dashboard` принимает Dota Friend ID (1…4294967295) или Steam ID64. ID64 преобразуется вычитанием 76561197960265728. Vanity URL намеренно не поддерживается. Сначала загружается `/players/{account_id}`, затем `/players/{account_id}/matches?limit=100&significant=1` с повторяющимся `project` для hero_id, start_time, kills, deaths, assists, gold_per_min, xp_per_min. OpenDota при проекции исключает часть стандартных полей, поэтому каждое из используемых полей запрошено явно. Справочник — `/heroStats`. Сервер никогда не подменяет ответ фикстурой. Демо-данные frontend доступны исключительно через `?demo=1` и подписаны на странице.

Winrate = число побед / число матчей с известным результатом × 100. Radiant определяется по `player_slot < 128`, результат сравнивается с `radiant_win`. Неизвестный результат исключён из знаменателя. KDA = среднее индивидуальных `(kills + assists) / max(1, deaths)`. GPM/XPM — арифметическое среднее только непустых значений, включая настоящий 0. Для каждой метрики передаётся количество наблюдений. Рейтинг берётся из `rank_tier`; MMR и изменение MMR не выводятся. Статистика героев считается по той же выборке до 100 матчей, а не за всё время. Клиентские фильтры влияют только на таблицу, не на обзор и график; это видно в подсказках.

## Детали матча

`GET /api/matches/{id}` проверяет положительный ASCII-числовой ID до 2^53−1 до обращения к источнику. Сервис OpenDota получает `/matches/{id}`, нормализует ответ через отдельные MatchDetail/MatchPlayer schema и кэширует готовый результат 120 секунд. Проверяются совпадение ID, уникальность/диапазон слотов, неотрицательные целые показатели. Неизвестные значения остаются null; anonymous account_id=0 нормализуется в null. 404/403 преобразуются в match_unavailable, лимиты/транспортные ошибки используют общий adapter. Ошибочные ответы не кэшируются.

Преимущество Radiant по золоту/опыту берётся из массивов источника: отрицательный знак означает преимущество Dire. Используется переданная временная шкала players.times подходящей длины; при её отсутствии — документированная минутная шкала. Некорректный ряд скрывается с уведомлением; отсутствующие точки не интерполируются. Наличие parse version не гарантирует заполнение всех полей.

`GET /api/match-items` независимо кэширует публичный справочник предметов; существующий `/heroes` используется повторно. Ошибка справочника не мешает показывать матч с ID. Новых таблиц, зависимостей и очередей разбора нет.

Frontend `/matches/:matchId` поддерживает прямое открытие и reload. Параметр player задаёт только выделение публичного игрока, не авторизацию. MatchHistory хранит result/hero/lobby/period/page в URL Dashboard; from содержит обратный относительный адрес только Dashboard и проверяется по allowlist. Синтетические demo-матчи не имеют ссылок на детали; прямой URL с demo=1 не обращается к API матча.

## Авторизация

`/auth/steam/login` создаёт случайное состояние на 10 минут: хэш в БД и HttpOnly SameSite=Lax cookie. Callback проверяет совпадение cookie, атомарно удаляет состояние с `DELETE RETURNING`, проверяет точный `return_to`, endpoint Steam, namespace, mode, signed fields, соответствие claimed_id/identity и свежесть nonce. Подтверждение выполняется POST-запросом `check_authentication` только к фиксированному HTTPS endpoint Steam. Отрицательный ответ, таймаут и повтор callback отклоняются. Пароль Steam и Web API key для этого потока не нужны.

Сессия — случайный непрозрачный токен на 7 дней, в БД хранится SHA-256. Нет токенов в localStorage. Выход и удаление требуют точного Origin frontend; `/me` и удаление требуют действующей сессии. Удаление транзакционно отзывает все сессии аккаунта. Просроченные записи очищаются при начале нового входа. Создание аккаунта использует атомарный `INSERT ON CONFLICT DO NOTHING`; одновременные первые входы проверены на настоящей PostgreSQL.

State проверяется как ровно 43 ASCII URL-safe символа до `compare_digest`: некорректный Unicode не приводит к 500. Повторяющиеся query-параметры отклоняются до потребления state. Отмена, истечение state и отрицательная/неудачная проверка Steam возвращают 303 на фиксированный frontend Dashboard с серверным кодом `auth_error`; браузер показывает локальное сообщение и повторный вход. Содержимое assertion и state в URL frontend не передаётся. Удаление cookies сохраняет Secure, HttpOnly, SameSite и Path исходной cookie.

## Инфраструктурные границы

- HTTP timeout 10 секунд на операцию, до 3 попыток при сетевых ошибках/5xx с задержками 0.25/0.5 секунды. 429 не повторяется.
- Общий ограниченный кэш: TTL 120 секунд, до 512 записей, только успешные ответы. Один lock ограничивает одновременную загрузку OpenDota. Это простая консервативная реализация для одного worker.
- Скользящее окно запросов: по умолчанию 30 в минуту на адрес соединения, до 10000 адресов. `/api/health` исключён, чтобы пользовательские запросы не блокировали readiness. По умолчанию proxy headers игнорируются. Opt-in `CLIENT_IP_SOURCE=railway` принимает один синтаксически корректный `X-Real-IP` при эксклюзивном Railway HTTP ingress; некорректный, отсутствующий или повторный заголовок возвращает ключ адреса соединения. Это настройка границы доверия, не средство авторизации; private ingress от недоверенных сервисов/TCP proxy недопустимы. Полная схема — в deployment-документе. Запуск одного worker обязателен до перехода на общий cache/limiter.
- CORS — явный список origins, cookies credentials, GET/POST/DELETE. Production требует HTTPS и Secure cookie. Frontend/backend должны быть на одном site, например app.example.com и api.example.com; раздельные railway.app и произвольный домен могут блокировать SameSite cookie. Не отключайте защиту браузера: настройте домены.
- JSON-логи не содержат query string, Steam ID, имён, cookies или секретов; access-log Uvicorn отключён. Ошибки БД возвращают 503 без исключения/DSN.
- OpenAPI `/docs`; `/api/health` проверяет подключение БД. Миграции применяются до запуска, не через `create_all` в production.

## Подготовленный вариант размещения

Один Railway web-сервис содержит API и собранный frontend, отдельный PostgreSQL Railway. Корневой multi-stage Dockerfile компилирует Vite с `/api`; Python image содержит только backend и `static`, запускается как непривилегированный пользователь. `railway.json` использует pre-deploy migration и healthcheck. Supabase не нужен: его Auth/Data API/Storage текущий продукт не использует. Отдельный API-only Dockerfile остаётся доступным для альтернативного размещения.

`STATIC_DIR` необязателен. При его задании приложение проверяет наличие `index.html` и монтирует frontend после API/документации. SPA fallback разрешён только для GET/HEAD навигации с Accept text/html и без расширения файла. Неизвестный API, отсутствующие assets, скрытые файлы и traversal возвращают ошибку. Разделители пути нормализованы и проверены на Windows. Assets имеют immutable cache, HTML — no-cache; API — no-store. Production добавляет HSTS, запрещает незащищённые origin/cookies и требует FRONTEND_URL в CORS allowlist.

Собранный frontend с backend проверяется локально через `scripts/start-production-preview.ps1` на 8001. Это HTTP-проверка того же пути раздачи, а не эмуляция Railway TLS. Docker runtime и настоящая Railway-инфраструктура требуют отдельной проверки после подключения аккаунта.

## Модули после этапа 1

По запросу пользователя локальная разработка продолжена без размещения Railway. Meta Lab теперь имеет собственные API/schema/service и frontend feature. Новых таблиц БД нет; пул хранится в браузере. Подробная методика и границы — в [meta-lab.md](meta-lab.md).

| Модуль | Будущая ответственность | Зависимости |
|---|---|---|
| Meta Lab (первая версия реализована) | Паблики/pro/Turbo, ранги, размеры выборок, фильтры и локальный пул, справочник патчей | Общий snapshot OpenDota heroStats; STRATZ и исторические сравнения пока не подключены |
| AI Coach | Объяснимые рекомендации, планы, сравнения | Валидация выборок, серверные лимиты, согласие пользователя |
| Challenges | Проверка матчей, XP, достижения | Детерминированные правила и журнал выдач |
| Community | Дружба, команды, приглашения | Account, ACL, модерация |
| Telegram | Подписки на уведомления, Mini App | Проверка Telegram initData, consent |
| Billing / Pro | Подписки, права, webhooks | Подписанные идемпотентные события; серверная проверка entitlement |

Новые модули должны оставаться внутри монолита, получать доступ к статистике через сервисный слой и иметь собственные миграции. Текущее `plan=free` — метаданные аккаунта, платных API нет. STRATZ не подключён: для этапа 1 достаточно OpenDota; будущие ключи STRATZ хранятся только на сервере. Не создавать фиктивные оплаты или AI-ответы ради навигации.
